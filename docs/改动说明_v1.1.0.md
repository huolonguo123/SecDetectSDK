## 1. 代码完整性校验(新检测项 11 `integrity`)

**目标**:inline hook 改的是"运行中的内存",文件签名/哈希查不出来;要拿内存和磁盘对拍。

**实现**(`src/det_integrity.cpp`)

| 函数 | 外号 | 干什么 |
|------|------|--------|
| `IntegrityDetector::run()` | 对拍器 | 遍历目标进程 maps 的可执行**文件**映射,逐页比对内存与磁盘同偏移字节 |
| `trusted_no_compare()` | 免检名单 | `/dev/`、`/proc/`、`/sys/`、`memfd:`、`anon_inode:` 不做对拍(不是普通文件) |

- 比对粒度 4KB(一页);单映射上限 8MB、一次总预算 64MB(防卡死);
- 命中时报 `va`、**文件偏移 = `off + (va - start)`**(可直接拿去 IDA 定位)、以及 mem/disk 前 4 字节;
- 没命中也会输出"比较了多少个映射/多少字节",证明这次是真扫了而不是跳过。

**证据链**(为什么成立)

1. `mmap(file)` 是按需分页 + **写时复制(COW)**:没被写过的页读出来 = 文件内容;有人往 `.text` 写跳板指令 → 该页 COW 出去,内存与磁盘不再相等;
2. `/proc/<pid>/maps` 行的 `offset` 字段就是**这段映射在文件中的起始偏移**,于是恒等式成立:
   `内存 VA 处字节 == 磁盘文件 (off + VA - map_start) 处字节`;
3. 差异点 = 被改写点,通常正好是函数入口(改 4~16 字节跳板)。

**验证**

```bash
adb shell su -c /data/local/tmp/secdetect integrity          # 扫自己
adb shell su -c /data/local/tmp/secdetect integrity pid:<pid> # 扫别的进程(需 root)
# 先跑一次干净基线,再用 frida/gdb 下断点改字节,应看到 "code diff @va=... file=..."
```

**局限**:只对文件映射有意义(匿名 JIT 段没有磁盘基线,由第 3 项的匿名执行组覆盖);`.data.rel.ro`/GOT 是 rw 段,不在本项范围(GOT hook 要与文件比 `.got`,属下一步)。

## 2. Root/Magisk:隐藏 root 之后仍可检测(检测项 1 增强)

**目标**:Magisk 的 DenyList 会把目标进程 namespace 里的 magisk 挂载**摘掉**,所有"扫文件/扫路径"的检查都会落空。

**实现**(`src/det_root.cpp`)

| 组 | 外号 | 干什么 |
|----|------|--------|
| L1 | 路径扫描 | su 二进制常见路径(兼容老式 root) |
| L2 | 载荷扫描 | `/debug_ramdisk/magisk`、/sbin/.magisk、/cache/magisk.log 等 |
| **L3** | **属性枚举** | `__system_property_foreach` 全量枚举属性,名字或值含 magisk/zygisk/riru/kernelsu/apatch/… 就报 |
| **L4** | **命名空间差分** | `/proc/self/mountinfo` vs `/proc/1/mountinfo`:init 有、我没有的挂载 = "有东西专门为我卸掉了" |
| L4b | 异常挂载 | tmpfs/overlay 出现在 `/`、`/system*`、`/vendor*`、`/product*`(真机是 erofs/ext4/只读 bind) |
| L5 | SELinux 域 | `/proc/self/attr/current` 是 `u:r:magisk:s0` / `:su:` |
| L6 | root 数据目录 | `/data/adb/magisk`、`/data/adb/ksu`、`/data/adb/ap`、`/data/adb/modules/*` |
| **L7** | **启动链旁证** | `verifiedbootstate=orange`、`flash.locked=0`(解锁是刷 Magisk 的前提,DenyList 挡不住) |

**证据链**(为什么"隐藏了还能查到")

- DenyList 隐藏的是**文件与挂载**,不隐藏**属性区**;属性区还能全量枚举 → L3 不看名字也能命中;
- Magisk 只在**目标进程的 namespace** 里卸载挂载,**init(pid 1)的 namespace 里那些挂载还在**;把两张 mountinfo 一减,差集就是"被隐藏"这件事本身的物证 → L4;
- 属性可被 `resetprop` 篡改,所以 L3 与 L7/L4 互为交叉验证:只有 properties 一处异常可疑,C 组证明"确实解锁过"。
- 实测锚点(Magisk 30.7,本机 Pixel 7):`init.svc.magiskd` 早已没有、su 路径表也已消失,主证据是 `/debug_ramdisk/magisk` + 属性/命名空间差分。

**验证**

```bash
adb shell su -c /data/local/tmp/secdetect root
# 隐藏验证:Magisk → 设置 → 配置 DenyList,勾上目标 App/进程后再跑,应看到
#   L3 prop[...]: ro.magisk.* / L4 hidden mounts: init has N mount(s) ... / L7 boot chain
getprop | grep -iE "magisk|zygisk|riru|kernelsu"     # 手工对照
cat /proc/self/mountinfo | head; cat /proc/1/mountinfo | wc -l  # 需要 root
```

**局限**:`resetprop` 能删属性字段;KernelSU/APatch 是内核态实现,用户态痕迹更少,主要靠 L4/L7;读 `/proc/1/mountinfo` 需要 root(非 root 时该项会输出"namespace diff skipped"提示,不会误报)。

## 3. USB:JNI 查"是否连接"、Java 查"USB 调试是否打开"(检测项 9)

**目标**:把三件容易混淆的事分开——①数据线插着吗 ②USB 调试(ADB)开着吗 ③adbd 真在跑吗。

**实现**

| 文件/函数 | 外号 | 干什么 |
|-----------|------|--------|
| `util::usb_physically_connected()` | 插线探测 | 读 `/sys/class/power_supply/usb/online|present`、`/sys/class/android_usb/android0/state`(native,不需 Java) |
| `SecDetectBridge.readUsbConnected(ctx)` | Java 插线探测 | `UsbManager.getDeviceList()`,退路 `ACTION_BATTERY_CHANGED` 的 `EXTRA_PLUGGED` |
| `SecDetectBridge.readAdbEnabled(ctx)` | **ADB 开关** | `Settings.Global.ADB_ENABLED`(**必须 Java**,native 拿不到) |
| `SecDetectBridge.readDevelopmentSettings/readMockLocation` | 开发选项 | `DEVELOPMENT_SETTINGS_ENABLED`、`ALLOW_MOCK_LOCATION` |
| `nativeSetEnvFacts(int[], String[])` | 回填口 | JNI 把上面采到的值填进 `sec_env_facts_t` 交给 `secdetect_set_env_facts()` |
| `UsbDebugDetector::run()` | 判定器 | 合并 native 属性/端口证据 + Java 回填事实 |

- native 侧仍保留:`persist.sys.usb.config`/`sys.usb.config` 含 `adb`、`ro.debuggable=1`、`ro.secure=0`、`service.adb.tcp.port`、5555/5554 监听(+归属进程);
- 没回填时输出提示并尝试 `settings get global adb_enabled` 兜底,不猜。

**验证**

```bash
adb shell su -c /data/local/tmp/secdetect usb_debug      # native 部分
adb shell su -c /data/local/tmp/secdetect env            # 看 Java 回填了什么
# Java 侧:SecDetectJava.prepare(ctx) 之后再 scan(),能看到 "java: Settings.Global.ADB_ENABLED=1"
adb shell settings get global adb_enabled                # 手工对照
```

**局限**:`sys.usb.config` 是功能开关,不等于"此刻有会话";部分机型 sysfs 节点名不同(已列多路探测 + Java 兜底)。

## 5. 魔改版 Frida(strongR 等):把"魔改点"当检测点(检测项 3 的 `[scan]`/`[memfd]`/`[anon]`/`[thread]`)

**思路**:魔改的目标就是"不让你按名字找到它",所以任何单一特征都会被改;要抓的是**改名成本高 / 改不掉的结构性不变量**:

| 魔改动作 | 留下的检测点 |
|----------|--------------|
| 把 `frida:rpc` 换成 base64(`ZnJpZGE6cnBj`)或随机串 | 特征表**同时放明文与 base64**;更狠的做法是直接找"名字无关"的结构(下面两行) |
| 改 agent 模块名/不落盘 | `/memfd:` 可执行映射、`(deleted)` 映射、**非运行时常态的匿名可执行段** |
| 改线程名 / 不命名线程 | 匿名可执行段 + JIT 特征内存 + rwx 段 |
| 保留 gum(JS 引擎)符号 | `gum-js-loop` / `gum_module_load` / `GumScript` / `gum_script_backend` 字符串 |

`util::mem_scan_any()` 一遍内存同时匹配 N 个 needle(避免 N 次全量扫描),默认预算 24MB。

**证据链**:字符串是"最省事也最容易被改"的一层;越靠近"结构性"越难改 —— 顺序是:
`模块名/线程名(易改)` → `明文特征串(易改)` → `base64/自定义混淆(中等)` → **`匿名/memfd 可执行内存 + rwx(改不掉,除非不用注入)`**。

**局限**:魔改版可以把 gum 字符串也加密,那就只剩结构层(匿名执行/memfd/rwx);特征表需要随版本迭代(工程上应该把它做成可下发配置)。

## 7. 虚拟机/双开:核心是"一个进程里有几个应用"(检测项 6 重写,`src/det_vm.cpp`)

**核心判据**:正常 App 进程只会映射**自己**的 APK/so/oat。所以把 maps 里所有"应用来源路径"解析成包名,做集合差分:

| 路径形态 | 解析出的包名 |
|----------|--------------|
| `/data/app/[~~<hash>/]<pkg>-<hash>/…` | `<pkg>` |
| `/data/user/<n>/<pkg>/…` | `<pkg>` |
| `/data/data/<pkg>/…` | `<pkg>` |

- 集合里出现 **≥2 个不同包名** → 同进程托管多个应用 = 双开/多开(`same process hosts N apps: ...`);
- 出现 1 个 ≠ 自己的包名 → "进程映射了别人的包";
- `/virtual/` 路径出现 → guest 数据目录被 bind 进宿主(VirtualApp 结构);
- mountinfo 里出现 `/virtual/` 或 `/data/user/` 的 bind mount → 同上;
- 框架特征串:`com.lody.virtual`、`io.virtualapp`、`com.lbe.parallel`、`com.excelliance.dualaid`、`com.polestar.clone`、`com.miui.multi`、`com.qihoo.replugin`、`com.didi.virtualapk`、`com.tencent.shadow`、`taichi`、`com.vmos`、`virtual/parallel/clone/multi-app`;
- 容器化 VM prop:`waydroid`/`anbox`/`cuttlefish`/`vsoc`/`redroid`/`vmos`/`llvmpipe`;cgroup 含 docker/kubepods;
- **Java 补充**:`getPackagesForUid(myUid()).length > 1`(同 uid 多包) —— 这条连"同名双开(同包名不同实例)"也能抓,由 `SecDetectBridge` 回填。

**证据链**:双开的实现形态决定了它必须"在一个进程里加载第二个应用":要么映射 guest 的 APK/so(路径判据),
要么把 guest 数据目录 bind 进宿主(mount 判据),要么共用 uid(uid→包列表判据)。三条独立判据交叉,难以同时清理。

**验证**

```bash
adb shell su -c /data/local/tmp/secdetect vm
adb shell su -c /data/local/tmp/secdetect vm pid:<双开宿主pid>
```

## 8. Repack:v1/v2/v3 + 签名 MD5 指纹比对(检测项 7,`src/apk_signature.cpp` + `src/det_repack.cpp`)

**实现**

| 函数 | 外号 | 干什么 |
|------|------|--------|
| `util::apk_signature_info()` | 三方案解析器 | v1 解 PKCS#7 取证书;v2/v3 解 APK Signing Block 取证书;各算 MD5 + SHA-256 |
| `pkcs7_first_cert()` | DER 走位 | `ContentInfo→[0]→SignedData→certificates[0]` 取出第一张 X.509 的完整 TLV |
| `block_find_value()` | 签名块导航 | 魔数 `APK Sig Block 42` 前 24 字节取长度,按 id 找 `0x7109871a`(v2)/`0xf05368c0`(v3) |
| `signer_first_cert()` | signer 走位 | signer→signed data→certificates 第一张(长度前缀 + DER) |
| `util::md5_hex()` | 自实现 MD5 | 零依赖,证书 MD5 与 `keytool -printcert` 语义一致 |
| `RepackDetector::run()` | 比对器 | 校准模式打印指纹;比对模式支持 `md5 或 sha256`、多基线 `d1|d2`、大小写不敏感 |

**输入格式**

```
<apk_path>                                   校准:打印 v1/v2/v3 各自 md5/sha256
<apk_path>,<md5或sha256>                     比对:命中任一方案即算官方包
<apk_path>,<d1>|<d2>|...                      多基线(换签名/多签场景)
```

**验证(真实 APK 三路对照,已实跑)**

```bash
# ① 本 SDK(宿主端用同一份源码跑的对照程序)
any=1  schemes: v1=1 v2=1 v3=0
v1 md5=ceda68c1e174710aef58897dae6eab4f sha256=b4cb83b4dad99f997dbe872f013aa16c14eec41d167021f371f7e1330f273ee6
v2 md5=ceda68c1e174710aef58897dae6eab4f sha256=b4cb83b4dad99f997dbe872f013aa16c14eec41d167021f371f7e1330f273ee6
# ② 独立 Python 重新解析 APK Signing Block → 同上
# ③ openssl 从 v1 的 CERT.RSA 取证书 DER 后 md5sum/sha256sum → 同上 (CN = John Wu)
```

设备上:

```bash
adb shell su -c "/data/local/tmp/secdetect 7 /data/app/<pkg>/base.apk"
adb shell su -c "/data/local/tmp/secdetect 7 '/data/app/<pkg>/base.apk,<官方md5>'"
# 对照:apksigner verify --print-certs base.apk   /   keytool -printcert -jarfile base.apk
```

**证据链**:重打包必然重新签名,重新签名必然换密钥 ⇒ "证书指纹 ≠ 官方基线"就是铁证。
v1/v2/v3 是**三套独立的签名方案**(v1 在 META-INF、v2/v3 在 CD 前的签名块),现代包常只签 v2/v3,旧包只有 v1,所以必须三套都解析。

**局限**:只能证明"签名变了",不能证明"代码改了";需要调用方持有官方基线;双开/注入不改 APK 文件(属第 6/10/11 项)。

## 9. Bootloader + Google Key Attestation(检测项 8 + `KeyAttestation.java`)

**第一层:AVB 属性**(可被 resetprop 伪造)
`ro.boot.verifiedbootstate`(orange/red/yellow)、`ro.boot.vbmeta.device_state=unlocked`、`ro.boot.flash.locked=0`、`ro.boot.veritymode=disabled|logging`、`ro.secureboot.lockstate=unlocked`、`ro.oem_unlock_allowed=1`。

**第二层:Key Attestation(TEE 签名,伪造不了)**(`java/com/sec/detect/KeyAttestation.java` 取证书 +
`java/com/sec/detect/AttestationParser.java` 纯 Java 解析)

| 步骤 | 函数/文件 | 说明 |
|------|-----------|------|
| 生成带挑战的密钥 | `KeyAttestation.ensureAttestedKey()` | `setAttestationChallenge()`,优先 StrongBox,退 TEE |
| 判硬件密钥 | `KeyAttestation.probeHardwareKey()` | `KeyInfo.isInsideSecureHardware()`,无 TEE = 0 |
| 取证书链 | `KeyAttestation.collectAndPush()` | 遍历链,找带 OID `1.3.6.1.4.1.11129.2.1.17` 的证书 |
| 解析 ASN.1 | `AttestationParser.parseCertificate()` | 纯 Java、**零 Android 依赖** → 可在 PC 上对真实证书自测(见下) |
| 取值 | 同上 | `rootOfTrust(704)`:`verifiedBootState`/`deviceLocked`/`verifiedBootHash`;`705/706/718/719`:OS/补丁级别;索引 1/3:安全级别 |
| 回填 | `SecDetectBridge.nativeSetAttestation()` | 交给 native 判定 |

native 判定(`src/det_bootloader.cpp`):`verifiedBootState != Verified` / `deviceLocked=false` / `securityLevel=Software` /
`swEnforced=1` / `hw_backed_key=0` 任一条 → 风险;未回填时明确输出"请从 Java 回填"而不是猜。

**★ 实测发现并修掉的真 bug(AuthorizationList 是 EXPLICIT 标记)**

真实证书里,AuthorizationList 的带标签条目**外面还包着一层 TLV**:

```
tag 704(0xBF 85 40) 内容 = 30 4A { 04 20 <verifiedBootKey> 01 01 00 0A 01 02 04 20 <hash> }
                                ↑ 还包着一层 SEQUENCE
tag 705(0xBF 85 41) 内容 = 02 01 00      ← 还包着一层 INTEGER
```

第一版按 IMPLICIT 直接把 704 的内容当 RootOfTrust 的字段序列读 → `deviceLocked` / `verifiedBootState`
**读不到且不报错**,静默变成"未知" → **解锁的机器也检测不出来**(比崩溃更糟)。
修法:`AttestationParser.explicit()` 统一"再解一层"(对 EXPLICIT/IMPLICIT 都容错)。

发现方式 = 拿 **Google 官方测试证书**做交叉验证(`google/android-key-attestation`
仓库 `src/test/resources/der/*`),而不是只看自己的代码。

**验证记录(已实跑)**

| 验证 | 手段 | 结果 |
|------|------|------|
| native 判定链 | 宿主端注入 env facts 后跑 `det_bootloader`(6 种情形) | 干净 TEE → risk=0;`deviceLocked=0` / `vbs=Unverified` / `Software` / `hash 不符` → risk=1;未回填 → 明确提示不误报 |
| ASN.1 解析器 | 真实证书 `algorithm_EC_SecurityLevel_TEE/cert0.der`、`…StrongBox/cert0.der`、`algorithm_RSA_SecurityLevel_TEE/cert0.der` + Windows JDK21 编译运行 `AttestationParserSelfTest` | 三张全部 `[OK]`:`securityLevel=TEE` / `StrongBox`、`deviceLocked=0`、`verifiedBootState=Unverified(2)`、`patch=2019-07`;`ALL OK` |
| Java 层类型检查 | 用 28 个 `android.*` 桩类 + JDK21 `javac` 编译 5 个 java 文件 | 零 error |
| 端到端(TEE 实签发) | 需要真机 + App(KeyStore 要求 Context) | **未做** —— 见下方"怎么自己验" |

**怎么自己验(设备端,需要 App)**

```java
// onCreate 里
SecDetectJava.prepare(getApplicationContext());
Log.i("SecDetect", "attest: " + KeyAttestation.describe()
        + " err=" + KeyAttestation.collectAndPush());
Log.i("SecDetect", "bootloader: " + SecDetectJava.scanOne(SecDetectBridge.DETECT_BOOTLOADER, null));
// 或者直接看 native 视角:adb shell run-as <pkg> ... 不方便时用日志打印 secdetect 的 output
```

期望:已解锁的机器(如本机 Pixel 7 刷 Magisk 后)`attest: deviceLocked=false (TEE 证明 bootloader 已解锁)`
+ `verifiedBootState=Unverified|SelfSigned`;锁定的零售机应是 `Verified` + `deviceLocked=true` → `(clean)`。
也可以把证书导出后丢给 PC 上的自测:`java -cp out com.sec.detect.AttestationParserSelfTest my.der`。

**证据链**:属性来自 bootloader→cmdline→属性区,root 后能改;而 attestation 是**TEE 用安全世界私钥签的证书**,
里面写死了启动链状态,改了就验签失败 —— 这是这一项"不可绕过"的根因。

**验证**

```bash
adb shell su -c /data/local/tmp/secdetect bootloader
adb shell su -c /data/local/tmp/secdetect env      # 看 attest 字段是否已回填
# Java: SecDetectJava.prepare(ctx) → KeyAttestation.collectAndPush()
# 对照应用:Android 上装 "Key Attestation" 类 App 或 GrapheneOS Auditor
```

**局限(必须写进报告)**:本 SDK 只做"字段自解析",**没有验证证书链签名**。生产形态应是:
在服务端用 Google attestation 根证书验链 + 校验挑战值是本次下发的随机数(防重放)+ 校验 verifiedBootHash 与官方值一致。
生成密钥有开销(几十~上百毫秒),建议只做一次并缓存。

## 补充(2026-09-11 追加):重打包检测支持"免传 APK 路径"

**需求来源**:把 SDK 当 .so 集成进 App 后,不应该每次调用都手输 APK 路径。

**改动**

| 位置 | 改动 |
|------|------|
| `include/sec_detect_api.h` | 新增 `SEC_FACT_APK_PATH` / `SEC_FACT_APK_BASELINE` 与字段 `apk_path[]`(192B)/ `apk_baseline[]`(128B);input 说明改为"可选" |
| `src/det_repack.cpp` | 路径/基线来源优先级:**input → env facts**;支持多 split(路径用 `'|'` 分隔,逐个校验);无路径时给出明确提示而不是静默跳过 |
| `src/api.cpp` | `needs_input()` 机制移除:DETECT_ALL 把 input 传给每一项(pid-based 项自己解析 `pid:N`);repack 只有在"给了 input 但路径打不开"时才返回参数错误 |
| `jni/sec_jni.cpp` | `nativeSetEnvFacts` 的 strs 扩为 `[glRenderer, apkPath, apkBaseline]` |
| `java/…/SecDetectBridge.java` | 新增 `readApkPaths()`(sourceDir + splitSourceDirs 用 `'|'` 拼)与静态字段 `officialSignatureBaseline` |
| `java/…/SecDetectJava.java` | 新增 `checkRepack()`(不传路径);`scan(ctx, null)` 即可 |
| `demo/main.cpp` | 新增 `repack-auto` 子命令:把路径/基线塞进 env facts 后以 **input=NULL** 调 repack —— 不开 App 也能验证这条链路;`env` 子命令打印 apk_path/apk_baseline |

**为什么必须由 Java 给路径**:`/proc/self/exe` 指向 `app_process64` 而不是 APK;
`/data/app` 在 Android 10+ 是 0711(可执行不可列目录)→ native 无法自己拼出可靠路径。

**基线怎么定(写进文档,防踩坑)**:可用 = CI 固化 / 服务端下发 / 多基线 `d1|d2`;
**不可用 = 运行期"第一次跑就记住"** —— 第一次运行的包可能已经是重打包版,那样等于把攻击者指纹当官方基线。

**频率**:APK 在 `/data/app` 是只读挂载,安装后不变 → 启动时查一次 + 缓存,不需要周期扫描。

**宿主端验证(input=NULL,已实跑,5 种情形)**

| 情形 | 结果 |
|------|------|
| 只给路径(校准) | risk=0;打印 `source: java env facts` + v1/v2 指纹(与既有真值一致) |
| 路径 + 正确 md5 | risk=0;`signature matches baseline ... (official build)` |
| 路径 + 错误 md5 | risk=1;`signature MISMATCH (current md5=...) — apk was re-signed` |
| 多 split,第二个文件不存在 | apk[0] 比对通过、apk[1] 明确报 `file not accessible`;有基线时整体按风险上报 |
| 什么都不给 | risk=0;提示 `no apk path — pass input ... or let Java fill SEC_FACT_APK_PATH` |

**设备端验证命令**(runner,不需要 App)

```bash
adb shell /data/local/tmp/secdetect repack-auto /sdcard/original.apk
adb shell "/data/local/tmp/secdetect repack-auto '/sdcard/original.apk,ceda68c1e174710aef58897dae6eab4f'"
adb shell /data/local/tmp/secdetect env      # 看 apk_path / apk_baseline
```
详见 `docs/验证重打包.md` G 节。
