# SecDetectSDK v1.2.0 改动说明 —— 第 8 项 Bootloader:补上"验证侧"

> 本次改动只针对**检测项 8 `bootloader` 的第二层(Google Key Attestation)**:
> v1.1.0 里它只做"字段自解析"——把证书里的 `deviceLocked` / `verifiedBootState` 读出来就用,
> 既不验签也不回验 challenge。**能读到字 ≠ 能信这些字**:自己 openssl 签一张假证书、
> 或者把别人的旧证书喂进来(重放),那一层都会判"已锁定"。
> v1.2.0 补的正是这两件事:**逐级验签 + 根信任锚**,以及 **challenge 回验**。
> 代码位置:`D:\android detector`;产物:`libsecsdk.so` / `libsecsdk-jni.so` / `secdetect`。
> 验证环境:WSL + NDK r29(arm64-v8a,android-23);Java 侧用 JDK 11 对 `android.jar`(API 33,target 8)编译。

## 1. 验证侧:逐级验签 + 根信任锚(检测项 8 增强)

**目标**:证书里的 `deviceLocked=true` 是 TEE 填的、且被签名覆盖 —— 但前提是"这张证书真的由
Google 信任链签发"。不验签的话,攻击者自己生成一对密钥、自签一张证书、字段照抄,检测项照样通过。

**实现**(`java/com/sec/detect/KeyAttestationVerifier.java`,纯 Java、零 Android 依赖)

| 函数 | 外号 | 干什么 |
|------|------|--------|
| `verify(chainDer, nonce, roots)` | 总验官 | 解析链 → 排序 → 逐级验签 → 根信任锚 → challenge 回验 → 字段判定,返回 `Report` |
| `orderChain()` | 排链 | 按 subject/issuer 把"顺序不限"的证书排成 叶子 → 中间 → 根 |
| `Report.trusted()` / `ok()` / `verdict()` | 结论器 | `trusted` = 链可信 + challenge 匹配;`ok` = 再加"设备已锁定 + 启动链验证通过" |
| `loadCertificates*()` | 信任锚加载 | PEM(可多张)/ DER 都吃;`setTrustedRootsFromPem()` 走这里 |
| `base64Decode/Encode` | 自带 base64 | 不依赖 `android.util.Base64`,也不依赖 API 26 才有的 `java.util.Base64` |

- 链上每张证书都 `checkValidity()`,**但被 pin 的信任锚(根)过期不判失败**(PKIX 惯例:根是硬编码的,
  不参与信任推导的时效判断)。这条不是拍脑袋:实测发现 Google 官方测试根 `notAfter=2026-05-25`,
  而当前系统时间已 2026-09 —— 不这么处理的话测试永远红。
- `rootLooksLikeGoogle` 只是**线索**(subject 里能不能看到 Google 根 serial `f92009e853b6b045`),
  同时输出根证书的 SHA-256 指纹(`rootSha256`)—— 生产上正确的做法是**按指纹 pin**。

**证据链**(为什么这样判是对的)

1. 签名覆盖整张证书的 TBS,而 attestation 扩展就在 TBS 里 → **改扩展里一个字节,签名必然对不上**。
   这一点用 `--tamper`(翻一位)实测验证:字段照样读得出来,但 `chain=FAIL`。
2. 只验到"链内自洽"是不够的:**任何自签的链自己都能自洽**。所以必须有外部信任锚;
   没给根时本实现**一律判失败**(不给"假装通过"的余地)。
3. 链式信任的终点是根的公钥 —— 攻击者没有 Google 根私钥,也拿不到中间证书(attestation key)私钥,
   所以他造得出字段、造不出链。

**验证**(PC 上,不需要设备)

```bash
javac -d out java/com/sec/detect/AttestationParser.java \
             java/com/sec/detect/KeyAttestationVerifier.java \
             java/com/sec/detect/KeyAttestationSelfTest.java
# 正向:Google 官方 EC/TEE 测试链(cert0→cert3,最后一张是自签根)
java -cp out com.sec.detect.KeyAttestationSelfTest cert0.der cert1.der cert2.der cert3.der \
     --root cert3.der --nonce 616263
# 反向:改 leaf 一个字节,必须被验签抓到
java -cp out com.sec.detect.KeyAttestationSelfTest cert0.der cert1.der cert2.der cert3.der \
     --root cert3.der --nonce 616263 --tamper
```

**局限**:本实现只做"链式验签 + 信任锚 + 有效期 + 字段",**没有**做 PKIX 的吊销(CRL/OCSP)、
PathLenConstraint、EKU 等全套路径校验;服务端可直接换成 `CertPathValidator`(本类注释里写了)。
另外,客户端验签本身可被 hook —— 见第 6 节边界。

## 2. challenge 回验:从"读到了就扔"到"必须等于本次下发的 nonce"

**目标**:证书里的 `attestationChallenge` 是 TEE 把请求方给的字节原样写进 KeyDescription 的,
**并且这段内容被签名覆盖**。所以"证书里的 challenge == 服务端刚发的随机数"这件事,
攻击者改不了 —— 这是防重放的唯一抓手。

**实现**

| 位置 | 改动 | 说明 |
|------|------|------|
| `AttestationParser.java:152`(原) | `cur.next();` → `Tlv challenge = cur.next();` + 存进 `Result.attestationChallenge` | 之前这一行把 challenge **直接丢弃** |
| `AttestationParser.Result.challengeMatches(byte[])` | 新增 | 逐字节比对(`Arrays.equals`),给自检/服务端共用 |
| `KeyAttestation.setChallenge(byte[])` | 新增 | challenge 可注入;变更时自动**删除旧密钥并重办证**(challenge 绑在密钥/证书上) |
| `KeyAttestation.randomChallenge()` | 新增 | 无服务端时的退路:`SecureRandom` 32B |
| `KeyAttestationVerifier.verify(...)` | 新增 | **没有期望 nonce 时一律判 challenge 不通过** |

**证据链**

- 旧实现的 challenge 是 `"secdetect-" + System.currentTimeMillis()`:可预测(hook 掉时间就当常量),
  攻击者能在一台"正常的、bootloader 锁着的"备用机上**提前办一张固定题目的证书**存起来复用;
  而收到证书的一方**从不比对** challenge → 重放永远通过。
- 现在 `nonce == null` 时 verifier 判 `challengeOk=false` 而不是"跳过这条" —— 宁可判否,不假装通过。
  这样"必须由服务端出题"就变成了代码里的硬约束,而不是文档里的建议。
- 实测(官方测试链):不给 `--nonce` → `MISMATCH`(证书里是 `616263`);给 `--nonce 616263` → `MATCH`。

**局限**:service 端必须保证 nonce **一次性 + 短期过期 + 绑定会话**;客户端只能证明"证书里的题 == 我手上的题",
"我手上的题是不是服务端刚发的"只有服务端自己知道。

## 3. 上报整条链 + 启动链哈希基线

**目标**:服务端验签需要的是**证书链本身**(DER),不是客户端解析后的几个数字;
`verifiedBootHash`(启动链哈希)之前恒传 -1,"镜像有没有被改"这一项等于一直没生效。

**实现**

| 函数 | 干什么 |
|------|--------|
| `KeyAttestation.chainBase64()` | 返回整条链的 base64(leaf → 中间 → 根),供上报服务端;同时存进 `lastChain()` |
| `KeyAttestationVerifier.base64Decode()` | 服务端/自检侧解回 DER(自带实现) |
| `AttestationParser.Result.verifiedBootHash` | 之前只存**长度**,现在把**值**也带出来 |
| `KeyAttestation.setVerifiedBootHashBaselineHex(hex)` | 给官方基线时判 1/0;没给则 -1(未知,不误报) |

**证据链**:`verifiedBootHash` 是 TEE 对当前启动链算的哈希,只有与**官方基线**比才有意义;
基线(每个机型/系统版本的合法值集合)只能由 CI 生成或服务端下发 ——
所以"能不能判镜像被改"取决于服务端有没有基线,而不是客户端读不读得到哈希。

**局限**:和 APK 指纹基线同理 —— **不要**用"第一次跑到的值"当基线(第一次可能已经是被改过的镜像)。

## 4. 回填通道:`att_chain_verified` 三态(1 / 0 / -1)

**目标**:把"链验过了没有"这个结论送进 native,参与第 8 项判定;同时**不能误报**
(集成方没配 nonce 或没给信任锚时,不能因此报"链有问题")。

**实现**

| 位置 | 改动 |
|------|------|
| `include/sec_detect_api.h` | 新增 `int32_t att_chain_verified;`;`reserved[2]` → `reserved[1]`,**结构体尺寸不变、不破 ABI** |
| `src/env_facts.cpp` | 未置位 `SEC_FACT_ATTESTATION` 时把 `att_chain_verified` 回落为 -1 |
| `jni/sec_jni.cpp` | `nativeSetAttestation` 的 `ints[4] = chain_verified` |
| `java/com/sec/detect/SecDetectBridge.java` | 文档与参数说明(5 个 int) |
| `src/det_bootloader.cpp` | `0` → **判风险**并写清原因;`1` → 打一条说明(含"权威判定仍应在服务端");`-1` → 不判 |
| `java/com/sec/detect/SecDetectJava.java` | `prepareAttestation(nonce, googleRootPem, bootHashBaselineHex)` + `attestationReport()` |

**证据链**(为什么 0 是强信号)

攻击者要让检测通过,最省事的做法不是伪造 TEE(做不到),而是**喂一张要么自签、要么是别人旧证书**的链。
这两种在有 challenge 回验 + 根信任锚的情况下都会落到 `att_chain_verified=0` ——
注意此时**字段本身可能是"完美"的**(`deviceLocked=true`),只看字段永远发现不了。

**验证**(不需要设备,`tools/native_attest_smoke.cpp`,5/5 通过)

```
[PASS] A 未做自检(chain=-1),字段已锁定            risk=0
[PASS] B 自检通过(chain=1),字段已锁定             risk=0  证据含「chain verified」
[PASS] C 自检失败(chain=0),但字段看着是'已锁定'    risk=1  证据含「证书链验证失败」
[PASS] D 字段本身有问题(deviceLocked=0 / Unverified) risk=1
[PASS] E 软件安全级别(Software → 无真 TEE)         risk=1
```

## 5. 修复记录:env_facts 的"未置位=未知"契约漏了 `hw_backed_key`

**症状**:冒烟测试的 A/B 两条用例第一次是**红的** —— 第 8 项报了
`attest: 密钥非硬件支持 (isInsideSecureHardware=false)`,而用例里根本没设置这个字段。

**根因**:`src/env_facts.cpp` 的契约是"`provided` 位图之外的字段一律按未知处理",
但它只对 `att_*` / `gl_renderer` / `apk_path` / `apk_baseline` 做了回落,漏了 `hw_backed_key`。
走 JNI 桥(`sec_jni.cpp` 会先把整组 int 预置成 -1)时看不出问题;
但集成方**直接调 `secdetect_set_env_facts()`**、且不置 `SEC_FACT_HW_KEY` 时,字段留 0 会被当成
"非硬件密钥" → **误报风险**。

**修复**

```c
/* src/env_facts.cpp */
if (!env_has(SEC_FACT_HW_KEY)) g_facts.hw_backed_key = -1;
```

修完 A/B 两条用例转绿。这个 bug 是**验证侧的冒烟测试暴露出来的** —— 也是把它留在仓库里的理由。

## 6. 边界(和最该讲清楚的一句话)

**客户端自检 ≠ 权威判定。** 验签代码跑在攻击者的设备上,他 Frida hook 掉 `verify()` 或
patch 掉 `Report.ok()` 的返回值,就能让 `att_chain_verified` 恒为 1;
`verifiedBootHash` 的基线、服务端下发的一次性 nonce,客户端也拿不到、更不该持有。

所以本次改动把红线画在了代码里:

- 客户端做:采集(生成带 challenge 的密钥、取链)、解析字段、**自检**(逐级验签 + 根信任锚 + challenge 回验)、上报整条链;
- 服务端做:下发 nonce(一次性、短期过期)、验链、比 nonce、比基线、**签发结论**(token/分数)。

README 的「限制」一节与 `KeyAttestationVerifier` 头注释都写明了这条边界;`att_chain_verified=1`
也**不是**"不可伪造"的证明,只是"本次自检没发现问题"。

## 9. 补记(同日,两项非 attestation 的修复)

### 9.1 同步"多路径参数校验"(repack 第 7 项,来自桌面副本)

**目标**:`/data/app/<pkg>/base.apk` + 各 split APK 都要参与重打包指纹校验,所以 input 支持
`路径1|路径2[,...基线]`。旧实现只取**第一段**做存在性判断,结果:传多路径时整个字符串被当成一条
路径 → `file_exists` 失败 → **参数错误被误拦**(多 split 的 App 直接漏检)。

**实现**(`src/api.cpp` 的 `repack_input_ok()`):按 `'|'` 切分,**每一段都要去掉首尾空白(含 `\r\n`)
且真实存在**,全通过才合法;并把"空 input"与"非法 input"区分开 —— 空 input 走 Java 回填的
`SEC_FACT_APK_PATH` 自动模式(不是参数错误)。

**验证**(宿主真跑;`demo/main.cpp` 把 `SEC_ERR_PARAM(-1)` 映射成进程退出码 `2`)

| 用例 | 修复前 | 修复后 |
|------|--------|--------|
| `a.apk`(存在) | rc=0 通过 | rc=0 通过 |
| `a.apk\|b.apk`(都存在) | **rc=2 被误拦** | rc=0 通过 |
| `a.apk\|missing.apk` | rc=2 拦下 | rc=2 拦下 |
| `" a.apk\r\n \| b.apk "` | **rc=2 被误拦** | rc=0 通过 |
| 空 input | rc=0(env facts 自动模式) | rc=0(同) |

对比方式:用回退该函数的临时副本另编一份二进制,同一组用例各跑一遍(脚本见下)。

### 9.2 修复:第 3 项内存扫描"自命中"误报(真机必现)

**现象**(宿主整库冒烟首次跑出):
```
3|frida|frida: [scan] mem hit "frida:rpc" @0x637576a95c5d (/tmp/secdetect_host)
```
命中地址落在**扫描器自己的二进制**里 —— 也就是说它命中了自己的特征常量。

**根因**:`kFridaNeedles` 里的明文/base64 常量(`"frida:rpc"`、`"frida-agent"`、`"ZnJpZGE6cnBj"`…)
**就活在本模块的 `.rodata`**;而 `util::mem_scan_any()` 遍历目标进程**所有可读映射**做 `memmem`,
没有任何自身排除 —— 扫自己时必然自命中。真机上等效于"第 3 项每次都报 frida",是硬误报
(同理影响所有用内存字符串扫描的项,第 12 项 `ida` 也用同一套)。

**实现**(`src/util.cpp`):新增 `own_module_path()`(用本函数的地址在 `/proc/self/maps` 里定位自己
所在模块的路径,带缓存)+ `same_module()`(按完整路径或 basename 比较,兼容 linker 给的相对名),
扫描前跳过自身模块的全部映射。

**验证**:修复后 `all` 输出 `3|frida|(clean)`;`tools/host_smoke.sh` 里加了一条**专门回归**

### 9.3 顺手做的宿主整库冒烟工具(`tools/host_smoke.sh`)

### 10.3 真机验证的经验(下次直接用)

- **真机是唯一能暴露"原生机型常态"的地方**:AVF/pKVM、virtual A/B 属性、`/data/user/0` bind mount
  这三样在模拟器/宿主上都不存在,静态看代码永远发现不了 → 每加一条"文件/属性/maps/mountinfo"证据,
  都要在**原生机**上跑一遍并解释每一条命中。
- 判据写法:**系统机制类的路径(伪文件系统、系统属性区)不能当证据**;要么跳过,要么用更结构化的特征
  (例如 `/virtual/` 而不是 `/data/user/`)。
- `adb shell su -c "… | …"` 里带 `|` 的参数会被远端 shell 当管道 → 把用例写成脚本 push 上去跑。
- `all` 类聚合输出要有**每项上限**,否则单项证据过长会吃掉整个缓冲,后面几项"静默消失"。
