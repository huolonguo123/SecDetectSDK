# 服务端验签方案(配合 SecDetectSDK 第 8 项 Bootloader / Key Attestation)

> 客户端能做的到 `KeyAttestation.collectAndPush()` 为止:采集、解析、**自检**、上报。
> 本文件定义**另一半**:服务端怎么出题、怎么验链、怎么比基线、怎么签发结论。
> 客户端自检可被 Frida hook 绕过(把 `verify()` 改成恒 true),所以**权威判定只在这里**。
> 代码位置:`D:\android detector\java\com\sec\detect\KeyAttestationVerifier.java`(逻辑可直接复用/移植)。

---

## 1. 红线:为什么不能只在客户端做

| 事情 | 客户端能做吗 | 原因 |
|------|--------------|------|
| 采集(生成带 challenge 的密钥、取链) | ✅ 只能它做 | 密钥在设备 TEE 里,链只有设备能出 |
| 解析 KeyDescription 字段 | ✅ | 纯字节解析 |
| 逐级验签 / 比对 challenge / 比基线 | ⚠️ 能但不算数 | 验签代码跑在攻击者设备上 → hook/patch 即绕过;基线也不该放客户端 |
| **下发 nonce** | ❌ | 一旦客户端能自造题目,就能"预办证"(见 §6 攻击对照) |
| **出结论(token/分数)** | ❌ | 结论必须由攻击者碰不到的一端签发 |

一句话:**客户端取证,服务端裁决**。nonce 是服务端出题权,验签是服务端裁判权,基线是服务端档案权。

## 2. 协议(三接口)

```
POST /attest/challenge                    ① 出题
  请求: { "device_id": "...", "package": "com.example.app" }        (带登录态/会话)
  响应: { "nonce": "<base64 32B>", "ttl_ms": 60000, "alg": "secp256r1" }

POST /attest/verify                       ② 交卷(客户端把链交上来)
  请求: { "nonce": "<base64>",                // 回带,绑定本次会话
          "chain": ["<base64 DER>", ...],     // KeyAttestation.chainBase64() 的原样输出
          "device_id": "...", "package": "..." }
  响应: { "ok": true,                        // 只有 ok=true 才代表"设备确实锁定且启动链可信"
          "token": "<JWT,短期>",               // 后续业务请求带它;ok=false 时不发
          "device": { "verified_boot_state": "Verified", "device_locked": true,
                      "security_level": "TEE", "os_version": "Android 13 patch 2024-01",
                      "boot_hash": "<hex>", "root_fp": "<sha256>" },
          "deny_reason": null }              // ok=false 时的原因(见 §5 错误码)

GET  /attest/status                       ③ 观测(风控用)
  响应: { "locked": 0.98, "by_reason": { "challenge_mismatch": 12, "chain_fail": 3 } }
```

要点:
- ①②必须**同一登录态/会话**;`nonce` 只认服务端自己发出的那一个(存会话表,用完即删)。
- 客户端不解析也不校验结论,只负责把链和 nonce 送上。(客户端仍会做自检,但那只用于本地日志/降级提示。)

## 3. 服务端实现骨架(Kotlin / Spring 风格)

### 3.1 nonce 会话表(一次性 + 短期 + 绑定会话)

```kotlin
data class Challenge(
    val nonce: ByteArray,
    val sessionId: String,
    val issuedAt: Long,
    val expiresAt: Long,      // now + 60s
    val used: Boolean = false,
)

@Component
class ChallengeStore(private val clock: Clock = Clock.systemUTC()) {
    private val map = ConcurrentHashMap<String, Challenge>()   // 生产换成 Redis + TTL

    fun issue(sessionId: String): ByteArray {
        val nonce = ByteArray(32).also { SecureRandom().nextBytes(it) }
        val now = clock.millis()
        map[sessionId] = Challenge(nonce, sessionId, now, now + 60_000)
        return nonce
    }

    /** 取出并**立即作废**(一次性);过期/不存在/已用过都返回 null */
    fun consume(sessionId: String, presented: ByteArray): Challenge? {
        val c = map.remove(sessionId) ?: return null          // 一次性:取走即删
        if (c.used) return null
        if (clock.millis() > c.expiresAt) return null
        if (!MessageDigest.isEqual(c.nonce, presented)) return null   // 常数时间比较
        return c.copy(used = true)
    }
}
```

### 3.2 验链 + 比 nonce + 判字段

```kotlin
@Component
class AttestationVerifier(
    private val roots: List<X509Certificate>,              // Google attestation 根(可含多个,支持轮换)
    private val bootHashBaseline: Map<String, Set<String>> // key: 机型/系统版本 → 合法 bootHash 集合
) {
    private val cf = CertificateFactory.getInstance("X.509")

    fun verify(chainB64: List<String>, expectedNonce: ByteArray, deviceModel: String): Verdict {
        // 1) 解析 + 排序(叶子 → 根)
        val chain = KeyAttestationVerifier.orderChain(        // ← 可直接复用客户端的纯 Java 实现
            chainB64.map { cf.generateCertificate(ByteArrayInputStream(Base64.getDecoder().decode(it))) }
                .map { it as X509Certificate }.toTypedArray())

        // 2) PKIX 路径校验(生产版:吊销/EKU/PathLen 都交给它)
        val params = PKIXParameters(HashSet(roots.map { TrustAnchor(it, null) })).apply {
            isRevocationEnabled = false                       // 有 OCSP/CRL 时打开
        }
        val path = CertPathValidator.getInstance("PKIX")
            .validate(cf.generateCertPath(chain.toList()), params) as PKIXCertPathValidatorResult

        // 3) 解析 attestation 扩展 + 回验 challenge(逐字节)
        val parsed = KeyAttestationVerifier.parseFromChain(chain)   // 见客户端同款实现
        require(MessageDigest.isEqual(parsed.attestationChallenge, expectedNonce)) {
            "challenge_mismatch" }                                  // ★ 防重放的关键一步

        // 4) 业务判定
        val locked = parsed.deviceLocked == 1
        val verified = parsed.verifiedBootState == 0
        val hwLevel = parsed.securityLevelName() in setOf("TEE", "StrongBox")
        val hashOk = bootHashBaseline[deviceModel]?.contains(parsed.verifiedBootHashHex()) ?: false
        val patchOk = parsed.osPatchLevel >= MIN_PATCH[deviceModel].orZero()   // 防降级
        return Verdict(locked && verified && hwLevel && hashOk && patchOk, path, parsed)
    }
}
```

> 不想引 PKIX 的话,可以直接用客户端那套"逐级 `verify()` + 信任锚比对"的实现(它已经在
> Google 官方测试链和合成链上真跑过);上生产再逐步补吊销与路径约束。

### 3.3 控制器与签发

```kotlin
@RestController
@RequestMapping("/attest")
class AttestController(
    private val store: ChallengeStore,
    private val verifier: AttestationVerifier,
    private val tokens: TokenIssuer,          // JWT,10 分钟
) {
    @PostMapping("/challenge")
    fun challenge(@RequestBody req: ChallengeReq, auth: Auth): Map<String, Any> =
        mapOf("nonce" to Base64.getEncoder().encodeToString(store.issue(auth.sessionId)),
              "ttl_ms" to 60_000)

    @PostMapping("/verify")
    fun verify(@RequestBody req: VerifyReq, auth: Auth): Map<String, Any> {
        val nonce = Base64.getDecoder().decode(req.nonce)
        val c = store.consume(auth.sessionId, nonce)
            ?: return deny("challenge_expired_or_replayed")
        return try {
            val v = verifier.verify(req.chain, nonce, req.deviceModel)
            if (!v.ok) deny("device_not_trusted:${v.reason}") else
                mapOf("ok" to true, "token" to tokens.issue(auth.subject, v.device), "device" to v.device)
        } catch (e: Exception) {
            deny("chain_invalid:${e.message}")     // 不把内部细节完全回给客户端
        }
    }

    private fun deny(reason: String) = mapOf("ok" to false, "deny_reason" to reason)
}
```

## 4. 客户端侧对应调用(照抄即可)

```java
// ① 取题
String nonceB64 = httpPost("/attest/challenge", "{}").getString("nonce");

// ② 采集 + 本地自检 + 回填 native(自检结果只作本地日志/降级,不作权威结论)

        AttestationParser.fromHex(hex(nonceB64)),   // 或直接 base64 解出字节
        GOOGLE_ATTESTATION_ROOT_PEM,                // assets 里放根证书;也可由服务端下发
        null);                                      // 有官方 bootHash 基线时再传

// ③ 交卷:整条链原样上报

```

## 5. 判定语义与错误码(服务端要能自解释)

| deny_reason | 含义 | 说明 |
|-------------|------|------|
| `challenge_expired_or_replayed` | nonce 不存在/过期/已用过/不匹配 | 一次性表的正常拒绝;频繁出现 = 有人在重放 |
| `chain_invalid:*` | 链验签失败(自签、中间缺、签名不符) | 典型:自己 openssl 造链 |
| `challenge_mismatch` | 链是真的,但 challenge 不是本次的 | 典型:重放别人的真链 |
| `device_not_trusted:*` | 链可信但字段不满足(未锁定/未验证/Software/哈希不符) | 说明设备确实被改过 |
| `no_baseline` | 没见过该机型/版本的 bootHash | 运营问题:该补基线了,**别当风险** |

配套监控:`challenge_mismatch` 与 `chain_invalid` 的**比值**很有信息量 —— 前者高 = 有人在收集/重放证书,
后者高 = 有人在造链。两个都该进风控看板。

## 6. 攻击对照表(为什么这些措施是必要的)

| 攻击 | 手法 | 挡住它的是哪一层 |
|------|------|------------------|
| 自签假证书 | openssl 造链 + 把字段写成 locked/Verified | **逐级验签 + 根信任锚**(客户端自检也能挡) |
| 重放别人的真链 | dump 一台真锁机的链,hook `getCertificateChain` 返回它 | **challenge 回验**(链是真的,题不对) |
| 预办证 | 把客户端随机数/时间戳 hook 成固定值,提前在真锁机办一张 | **服务端出题 + 一次性 nonce** |
| hook 客户端自检 | 让 `verify()` 恒 true | 无关紧要:**判定不在客户端** |
| 真机代理农场 | 把请求实时转发给一台真锁机办证 | 设备指纹 + 行为风控 + 频率限制(本方案之外) |
| keybox 伪造 | 用泄露的 attestation 私钥签任意题目/字段 | **服务端也挡不住**(链会验过) → 靠 keybox 吊销名单 + 风控;这是 attestation 的最终边界 |

## 7. 运维与安全清单

- **传输**:全链路 HTTPS + 证书 pinning(否则中间人可把请求转发到真机农场)。
- **nonce**:一次性(取走即删)、TTL ≤ 60s、绑定会话与包名;比较用常数时间(`MessageDigest.isEqual`)。
- **时钟偏移**:TTL 判断留 ±30s 余量;客户端时间不可信,别用客户端上报的时间。
- **根证书**:Google 根会轮换 → 支持多张根 + 可热更新;并按 **SHA-256 指纹 pin**(别靠 subject 字符串,
  X500Principal 打印形式会变)。
- **基线**:`verifiedBootHash` 按机型/系统版本维护;**不要**用"首次见到的值"当基线(第一次可能已是被改过的镜像)。
- **降级**:同时卡 `osPatchLevel >= 基线`,防止用旧系统版本(已知漏洞)跑。
- **性能**:密钥生成 + 验签都是几十毫秒级,**按会话/登录做一次**,不要每帧调用;结果用短期 token 承载。
- **日志**:存 `root_fp`、`boot_hash`、`os_version`、`deny_reason`,便于回溯"这批设备发生了什么"。

## 8. 本地怎么先跑通(不依赖真机)

1. **正向**:`tools/make_synthetic_attestation_chain.py` 合成一条"已锁定 + Verified"的链,
   把 `nonce.hex` 当作服务端下发的题,在服务端 verifier 上应返回 `ok=true`。
2. **反向 1**:同一条链换一个 nonce → 必须 `challenge_mismatch`。
3. **反向 2**:`--tamper` 改 leaf 一个字节 → 必须 `chain_invalid`。
4. **回归**:客户端侧 `tools/host_smoke.sh` + `KeyAttestationSelfTest` 的两个方向都要保持通过。

> 服务端实现可以直接照搬 `KeyAttestationVerifier`(纯 Java、无 Android 依赖、已在官方测试链与合成链上验过),
> 再把 PKIX 路径校验、吊销、基线库、token 签发补上。

## 9. 一页速查

```
出题:服务端 SecureRandom(32B) → 存会话表(60s TTL,一次性)
采集:客户端 AndroidKeyStore + setAttestationChallenge(该题) → 取链
交卷:整条链 base64 原样上报(不要只在客户端解析后上报数字)
裁决:① 逐级验签到 Google 根(信任锚按指纹 pin)
      ② 证书里的 attestationChallenge 必须 == 本会话那道题(防重放)
      ③ deviceLocked=true / verifiedBootState=Verified / securityLevel∈{TEE,StrongBox}
      ④ verifiedBootHash ∈ 官方基线,且 osPatchLevel ≥ 基线(防降级)
签发:全过才发短期 token;不过就别发,并记录 deny_reason
边界:hook 客户端无用(判定不在这儿);keybox 伪造连这里也挡不住 → 靠风控
```
