# 怎么验证"重打包检测"(检测项 7 `repack`)

验证分两件事,别混在一起:

- **A. 验证解析器对不对**(能不能正确读出 v1/v2/v3 的证书指纹)—— 用一个**已知答案**的 APK 对照;
- **B. 验证判定逻辑对不对**(换签名会不会报风险)—— 自己用**另一个密钥重签**一份当"攻击者样本"。

下面全程在 Windows PowerShell 里跑(你自己跑),手机命令用 adb。

---

## 0. 准备(一次性)

```powershell
# --- 你已有的:JDK1.8 的 keytool、SDK build-tools 的 apksigner/zipalign ---
# 找 apksigner / zipalign:
Get-ChildItem "$env:LOCALAPPDATA\Android\Sdk\build-tools" -Recurse -Include apksigner.bat,zipalign.exe |
  Select-Object -ExpandProperty FullName

# 设个工作目录 + 变量(按你的实际路径改)
cd "$env:USERPROFILE\Desktop"
$BT  = "$env:LOCALAPPDATA\Android\Sdk\build-tools\35.0.0"     # 换成上面查到的那版
$APK = ".\Magisk-v28.1.apk"                                   # 已知答案的样本(桌面上就有)
$KT  = "C:\Program Files\Java\jdk1.8.0_xxx\bin\keytool.exe"   # 你的 keytool 路径
```

把 runner 推到手机:

```powershell
adb push "D:\android detector\build\arm64\secdetect" /data/local/tmp/
adb shell chmod +x /data/local/tmp/secdetect
adb push $APK /sdcard/original.apk    # 放 /sdcard,普通 shell 就能读,不用 root
```

---

## A. 先证明"解析器是对的"——用已知答案的 APK

**A1. 在设备上跑校准模式**(不带基线 = 只打印指纹,不判风险):

```powershell
adb shell /data/local/tmp/secdetect 7 /sdcard/original.apk
adb shell "/data/local/tmp/secdetect 7 /sdcard/original.apk"   # 等价的引号写法
```

**Magisk-v28.1.apk 的正确输出(已用三路独立工具核对过,直接对照)**:

```
== repack (7) ==
  verdict: OK    (0, no risk found)
  evidence: schemes: v1=yes v2=yes v3=no;
            v1 cert md5=ceda68c1e174710aef58897dae6eab4f sha256=b4cb83b4dad99f997dbe872f013aa16c14eec41d167021f371f7e1330f273ee6;
            v2 cert md5=ceda68c1e174710aef58897dae6eab4f sha256=b4cb83b4dad99f997dbe872f013aa16c14eec41d167021f371f7e1330f273ee6;
            fingerprint(calibration): take one of the md5/sha256 above as baseline
```

要点(**v1 与 v2 的指纹必须相等** —— 同一把密钥签名,两套方案解析出来的证书是同一张):
- 两个都相等 → 说明 v1(PKCS#7 DER 走位)和 v2(APK Signing Block 解析)都对;
- `v3=no` 正常(Magisk 这个包没签 v3);
- 若出现 `v1=no` 而你知道它是老包 → 说明解析有问题(这类包**必须**有 v1)。

**A2. 用 PC 工具独立复核(三方交叉,推荐做一次)**

```powershell
# v1 证书指纹(keytool 从 jarfile 读 PKCS#7;注意 keytool 只认 v1)
& $KT -printcert -jarfile $APK      # 看 "MD5:" 一行是否等于上面的 v1 cert md5

# v2/v3 证书指纹(keytool 看不到,要用 apksigner)
& "$BT\apksigner.bat" verify --print-certs $APK     # 看 "Signer #1 certificate SHA-256 digest"
```

三个来源(SDK / keytool 或 apksigner / 甚至 openssl)指纹一致 = 解析器可信。
**这一步的意义**:上一版就踩过坑——v1 签名文件是 deflate 压缩,代码用了错的解压 API,
v1 指纹永远取不到,只有 A1 里"v1 和 v2 必须相等"才能发现这种 bug。

## B. 验证"换签名会不会报风险"——自己做攻击者样本

原理:系统安装时校验签名,篡改过的包要能装上**必须整体重签**,所以"签名指纹变了"就是重打包的铁证。
验证方式就是**用你自己的密钥重签一遍**(不改代码也能验证机制,因为检测项只认签名)。

**B1. 造一个自己的密钥**

```powershell
& $KT -genkeypair -v -keystore .\my.keystore -alias attacker -keyalg RSA -keysize 2048 `
       -validity 3650 -storepass 123456 -keypass 123456 `
       -dname "CN=Attacker, OU=RE, O=Test, L=SH, C=CN"
```

**B2. zipalign + 用新密钥重签(这就是"攻击者的重打包")**

```powershell
Copy-Item .\original.apk .\repacked.apk -Force
# v2/v3 要求先对齐(对齐必须在签名之前做)
& "$BT\zipalign.exe" -p -f 4 .\repacked.apk .\repacked-aligned.apk
# 重签:v1+v2+v3 全签(schemes 会显示 v1=yes v2=yes v3=yes)
& "$BT\apksigner.bat" sign --ks .\my.keystore --ks-pass pass:123456 --key-pass pass:123456 `
    --v1-signing-enabled true --v2-signing-enabled true --v3-signing-enabled true `
    --out .\repacked-signed.apk .\repacked-aligned.apk
```

> 如果 apksigner 报 "already has a signature" 之类的错,说明旧 META-INF 签名文件还在,
> 用 7-Zip 打开 `repacked-aligned.apk`,把 `META-INF\` 下的 `*.RSA/*.DSA/*.EC/*.SF` 删掉再签即可。
> (新版 apksigner 一般会自动清理,先直接签,不行再删。)

**B3. 跑比对模式看判定**

```powershell
adb push .\repacked-signed.apk /sdcard/repacked.apk

# ① 用**原包指纹**当基线 → 预期 MISMATCH(风险)
adb shell "/data/local/tmp/secdetect 7 '/sdcard/repacked.apk,ceda68c1e174710aef58897dae6eab4f'"
# 预期: verdict: RISK (1) / repack: signature MISMATCH (current md5=...) vs baseline ...

# ② 用**新包的自己指纹**当基线 → 预期 matches(不误报)
adb shell /data/local/tmp/secdetect 7 /sdcard/repacked.apk          # 先取新指纹
adb shell "/data/local/tmp/secdetect 7 '/sdcard/repacked.apk,<上一步打印的新md5>'"
# 预期: verdict: OK (0) / repack: signature matches baseline ...

# ③ 用原包 + 原包自己的基线 → 预期 matches(不误报)
adb shell "/data/local/tmp/secdetect 7 '/sdcard/original.apk,ceda68c1e174710aef58897dae6eab4f'"
```

**退出码也能脚本判定**:命中风险 `echo $?`(PowerShell 里是 `$LASTEXITCODE`)为 1,干净为 0,参数错为 2。

**B4. 独立复核(证明不是检测器自己说变就变)**

```powershell
& "$BT\apksigner.bat" verify --print-certs .\repacked-signed.apk
```
对比 A2 里原包的 `Signer #1 certificate SHA-256 digest` —— 两份不同 = 确实换签名了,
与 SDK 报的 MISMATCH 结论一致。

## C. 顺带验证三种签名方案都能认(可选,但很能说明覆盖度)

```powershell
# ① 只签 v2/v3(现代包的常见形态,旧实现会漏报)
& "$BT\apksigner.bat" sign --ks .\my.keystore --ks-pass pass:123456 --key-pass pass:123456 `
    --v1-signing-enabled false --v2-signing-enabled true --v3-signing-enabled true `
    --out .\v23only.apk .\repacked-aligned.apk
adb push .\v23only.apk /sdcard/
adb shell /data/local/tmp/secdetect 7 /sdcard/v23only.apk
# 预期: schemes: v1=no v2=yes v3=yes + v2/v3 指纹(仍能比对,不再漏报)

# ② 只签 v1(老包形态)
& "$BT\apksigner.bat" sign --ks .\my.keystore --ks-pass pass:123456 --key-pass pass:123456 `
    --v1-signing-enabled true --v2-signing-enabled false --v3-signing-enabled false `
    --out .\v1only.apk .\repacked-aligned.apk
adb push .\v1only.apk /sdcard/
adb shell /data/local/tmp/secdetect 7 /sdcard/v1only.apk
# 预期: schemes: v1=yes v2=no v3=no(v1 走 PKCS#7 取证书,deflate 也能解出来)
```

## D. 验证"真实 App 的路径"(装到手机上跑)

签名不同的包**不能覆盖安装**,要先卸原包(或用别的包名/新建工程)。

```powershell
adb shell pm list packages | Select-String 你要的包
adb shell pm path com.example.app          # 得到 /data/app/.../base.apk
adb shell su -c "ls -l /data/app/~~*/com.example.app-*/base.apk"   # 读 /data/app 需要 root
adb shell su -c "/data/local/tmp/secdetect 7 /data/app/<pkg>/base.apk"      # 校准拿官方基线
# CI/发布侧应把这条基线固化,运行期用比对模式
```

App 内(JNI)路径:

```java
SecDetectJava.prepare(ctx);
String base = SecDetectJava.signatureMd5(ctx);            // 或 signatureSha256
// 与固化基线比对(基线由 CI 从发布包生成):
SecDetectJava.scanOne(SecDetectBridge.DETECT_REPACK,
        ctx.getApplicationInfo().sourceDir + "," + base);
```

## E. 容易踩的坑

| 现象 | 原因 / 处理 |
|------|-------------|
| `repack: input required` / 返回码 -1 | 没传 APK 路径,或路径不存在(api 层会先校验文件存在);路径带空格要整体加引号 |
| `module: cannot read maps` | 无关;但读 `/data/app/...` 需要 `su -c`,普通 shell 读不了 |
| `info: no v1/v2/v3 signature found` | 包确实没签名(v4 签名 / 仅 v3.1),或文件被截断;换包试 |
| `v1=no` 但 keytool 说它有 v1 | 解析 bug(上一版就是这样),要修而不是当正常 |
| MISMATCH 但 apksigner 显示证书相同 | 基线的算法/大小写不对:MD5 是 32 位 hex、SHA-256 是 64 位 hex,均小写(输入大小写不敏感) |
| 重新签名后尺寸/对齐变了 | 正常。v2/v3 签的是"除签名块以外的内容",签名后**不要再动文件** |
| 用同一密钥重签同名包,指纹会一样 | 指纹是**证书级**的,所以同密钥重签不会被判重打包——这恰好说明该判据的语义边界:它抓的是"换密钥",代码级篡改要靠第 11 项代码完整性 |

---

## F. 一句话总结验收标准

1. 设备上对 Magisk-v28.1.apk 跑 `secdetect 7`,输出里 **v1 与 v2 的 md5/sha256 必须完全相等**,
   且与 keytool / apksigner 一致 → 解析器可信;
2. 同一包用自己的指纹当基线 → **OK(不误报)**;
3. 换密钥重签后的包 + 原包指纹当基线 → **RISK / MISMATCH**(退出码 1),apksigner 输出也证明证书换了;
4. `--v1-signing-enabled false` 造的 v2/v3-only 包 → 显示 `v1=no v2=yes v3=yes` 且仍能比对 → 覆盖了三套方案。

## G. 验证"不传 APK 路径"的 App 集成形态(免传参模式)

App 里 repack 项的路径与基线由 Java 回填(env facts),`secdetect(DETECT_REPACK, NULL, ...)` 即可。
**不用写 App 也能先在设备上验证这条链路** —— runner 有 `repack-auto` 子命令,它做的正是
"把路径/基线塞进 env facts,然后以 input=NULL 调用":

```powershell
# 1) 只给路径(等价 Java 只回填 SEC_FACT_APK_PATH)→ 校准模式,打印指纹
adb shell /data/local/tmp/secdetect repack-auto /sdcard/original.apk
# 预期: source: java env facts (SEC_FACT_APK_PATH); schemes: ...; fingerprint(calibration)

# 2) 路径 + 正确基线(等价 Java 同时回填 APK_PATH 与 APK_BASELINE)→ OK
adb shell "/data/local/tmp/secdetect repack-auto '/sdcard/original.apk,ceda68c1e174710aef58897dae6eab4f'"
# 预期: signature matches baseline ... (official build)  → 退出码 0

# 3) 路径 + 错误基线(模拟"装的是重打包版")→ RISK
adb shell "/data/local/tmp/secdetect repack-auto '/sdcard/repacked.apk,ceda68c1e174710aef58897dae6eab4f'"
# 预期: signature MISMATCH ... → 退出码 1

# 4) 看 env facts 里到底有什么
adb shell /data/local/tmp/secdetect env     # 会打印 apk_path / apk_baseline 两行
```

多 split APK(每个 split 都是独立签名的文件,必须逐个校验):

```powershell
adb shell "/data/local/tmp/secdetect repack-auto '/data/app/~~x/com.a-1/base.apk|/data/app/~~x/com.a-1/split_config.arm64_v8a.apk,<基线>'"
# 预期逐条输出 apk[0] / apk[1];某条读不到会明确报 "file not accessible"(读 /data/app 需要 su)
```

**基线怎么定(重要,别搞错)**

| 做法 | 是否可用 | 说明 |
|------|---------|------|
| CI 对发布包跑一次校准模式,把指纹写进构建常量 | ✅ 推荐 | 指纹是**证书级**的,只要签名密钥不变,发新版包指纹不变 → 固化一次长期有效 |
| 服务端下发基线 | ✅ 最灵活 | 能对付密钥轮换、可随时更新,还能防"本地被 hook 成恒返 0" |
| 运行期"第一次跑就记住当前指纹" | ❌ **错误** | 第一次运行的包可能已经是重打包版 → 把攻击者指纹记成官方基线,以后永远不报 |
| 多基线 `d1|d2` | ✅ | Play App Signing / 换签密钥的历史指纹都放进去 |

**频率**:APK 装在 `/data/app` 且是只读挂载,安装后不会再变 → **启动时查一次 + 缓存结果**即可,
不需要每次运行/每帧扫。真正的对抗点是"本地判断可被 hook",所以结果要上报服务端聚合裁决。
